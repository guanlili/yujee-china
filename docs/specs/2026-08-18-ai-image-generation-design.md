# AI 生图工具设计(第一版)

日期:2026-08-18
分支:main(未开)
状态:**待小雨确认**

## 背景

用户要的是「项目里一个用户可以用的工具」,能给封面、封底、背景和书里的图生成图片。
本设计只做其中一部分,拆分理由见「范围」。

设计前用火山 Seedream 4.0 实打实跑了 40 多张,以下结论都是实测,不是推断:

| 实测项 | 结论 |
|---|---|
| prompt 里出现 `book` / `cover` | 模型画出「一本书的实物照」——书脊、圆角、四边露白。8/8 全废 |
| prompt 里出现 `text` / `photo` / `portrait` | 模型把这些词画成乱码假字印在图上 |
| prompt 里出现十六进制色码 | 原样当文字印在图上。18/18 全中 |
| 负向词(`no flowers`) | **无效**,照样画出来 |
| 一次喂多个色 | 画成横向色块,不是统一色调的纹理 |
| `seed` 复现 | **不复现**。同 seed / 同 prompt / 同尺寸连出两张,是两块完全不同的布 |
| token 计费 | 随像素走。最小 921,600 px;720×1280 = 3600 tokens ≈ ¥0.072/张 |
| 一次调用出多张 | 无折扣(`sequential_image_generation: auto` 只给 1 张),多候选=线性成本 |
| Ark 国内直连 | 5.1s 出图 + 0.45s 下载 = **5.6s** |
| Ark 美国出口(≈ Vercel) | 12.7s 出图 + 4.3s 下载(137 KB/s)= **17s** |

前四条已经固化进 `apps/web/src/lib/imagegen/prompt-recipe.ts` 并有测试守着。

「seed 不复现」这条否掉了「先出小图给用户选、选中后用同 seed 复现成大图」的方案:
**候选即成品**,尺寸必须一次到位。

## 范围

**做:** 用户在编辑器里对着一个图槽,用自由文字描述生成一张图,存成本册的一张照片,
用来填这个槽。因为落点是图槽,封面、封底、内页图三种位置**同时**支持。

**不做(留给后续版本):**

- **页根背景(真·底图)** —— 这是第二版。`{{IMG_SRC:slotId}}` 那条路走的是 `<img>`,
  而页根背景是 CSS `background`。`src/lib/pdf/render-raster.ts` 的预烘只认
  `img[data-image-slot]`,分享备份只备份 photo,摊平和 Live 视频同理 —— 四条链路都要改。
  独立工程,不塞进第一版。
- **对话里按需生成** —— 第三版,design-agent 加写工具。
- **图生图 / 老照片修复** —— 另一条产品线。

## 核心判断:生成的图 = 一张用户没拍、但拥有的照片

生成成功后按 photoId 落 `photo-originals/{albumId}/{photoId}.jpg` + `album_photos` 表,
拿到一个与用户上传照片**完全同构**的 photoId。

这样做的收益:导出、分享快照、备份、滤镜、翻页视频、PDF 预烘 —— **下游一行不用改**,
因为对它们来说这就是一张照片。

反面参照:画板垫底背景(`boardbg-*`)那条路看起来更近,但
`src/lib/album/photo-original-sync.ts:19` 明确把 `boardbg-*` 排除在服务端同步之外,
它只存本机 IndexedDB。生成的图若走那条路,**用户换台设备图就没了** —— 那不是能收费的功能。

## 交互

1. 图槽的操作入口(桌面 EditorPort 图片菜单 / 移动端 EditView)新增「AI 生成」。
2. 弹窗:一个自由描述输入框 + 一行说明(这张图会放进当前槽位)。
3. **一次生成一张**(小雨拍板)。
4. 生成中走异步任务 + 轮询(复用现有 job 机制),不阻塞编辑。
5. 出图 → 预览 → 「用这张」(入库占槽)或「重来一次」。
6. **重来一次不额外扣费**,每次付费生成附带 **1 次**免费重生成。
   理由:自由描述的废图率注定不低,一次不中就净亏用户一分,口碑代价比成本大得多。
   次数定在 1 而不是 2,是被下面「尺寸与成本」那张表算出来的 —— 整页大图尺寸下
   给到 2 次免费(共 3 张)毛利就打平了。免费次数用尽后再生成,重新扣一分。

## 尺寸与成本

「候选即成品」意味着尺寸必须一次给到最终需要的大小。第一版规则:

**按目标槽位的宽高比生成,长边 2048;若算出的总像素低于 provider 下限则抬到下限。**
(Ark 下限实测 921,600 px;Gemini 的下限待核。)

页面真相是 794×1123,所以整页槽按 1448×2048 出,约合页面 CSS 像素的 1.8 倍,
够 PDF 导出栅格化用。小槽(如 mag-62 封面那个 212×402 的胶囊框)按比例缩,
但不低于下限。

成本随像素线性走(Ark 实测 token ≈ px/256,¥0.02/千 token):

| 尺寸 | 用途 | tokens | 成本 | 1 积分(¥0.71–1.07)的毛利 |
|---|---|---|---|---|
| 1448×2048 | 整页 / 大图槽 | 11584 | ¥0.232 | 3.1× – 4.6× |
| 同上 + 1 次免费重生成 | | | ¥0.46 | 1.5× – 2.3× |
| 同上 + 2 次免费重生成 | | | ¥0.70 | **1.0× – 1.5×(打平,不采纳)** |
| 720×1280 | 垫底背景(第二版才用) | 3600 | ¥0.072 | 10× – 15× |

**免费重生成定为 1 次就是这张表的结论。** Gemini 单价核实后这张表要重算,
如果 Gemini 明显更贵,免费重生成可能得取消 —— 那时要重新权衡口碑与毛利。

## Provider 抽象

生产和本地用不同的家,原因是网络地理:Web 部署在 Vercel(美国),产品是海外市场,
而 Ark 在北京 —— 生产链路要跨太平洋两个来回(见背景表最后两行)。

```
interface ImageProvider {
  generate(input: { prompt: string; size: string }): Promise<{ bytes: Uint8Array; mime: string }>
}
```

- **`gemini.ts`(生产)** —— Vercel→Google 同大洲;返回 `inlineData` base64,
  **没有第二趟下载**,直接省掉 Ark 那 4.3s / 137KB/s 的瓶颈。
- **`seedream.ts`(本地开发 + 离线批量)** —— 已写好并有测试。小雨本地在国内,
  直连 5.6s 反而是最优路径;`scripts/gen-board-bg.ts` 继续用它出素材。

按环境变量 `IMAGE_PROVIDER=gemini|ark` 选,默认 gemini。

## Prompt 约束外壳

用户的描述**不直接发给模型**,而是填进一个外壳:

```
buildUserImagePrompt(userText) = 承重墙前缀 + userText + 承重墙后缀
```

承重墙 = 背景表前四条固化下来的约束(满幅、不提文字类名词、单一主色、不用负向词)。
用户输入只提供内容,不能改结构 —— 包括不能靠 "ignore the above" 这类注入冲掉前缀。

## 扣费

沿用现有三件套,不造新机制:`GENERATION_HOLD` → 成功 `GENERATION_SETTLE` /
失败 `GENERATION_RELEASE`。`creditService.availableBalance` 已按「余额 − 在途预留」算。

**1 张 = 1 积分。** 与现有 `PHOTOS_PER_CREDIT = 1`(1 积分 = 1 张照片)完全同构 ——
生成的图就是一张照片,用户不需要理解任何新的计价概念。

毛利见上面「尺寸与成本」那张表:书里的图按 1448×2048 出,单张 ¥0.232,
含 1 次免费重生成后是 1.5×–2.3×。(Ark 实测价;Gemini 单价待核,见前置条件。)

免费重生成不额外 hold,直接复用同一笔已 settle 的扣费。

## 内容审核

自由描述意味着用户能让它生成任何东西 —— 这既是合规风险,也是成本泄漏
(有人会把它当免费通用生图 API 用)。两层:

1. **上游** —— Gemini 自带安全过滤。被拒视为失败:退积分、**不计入免费重生成次数**、
   提示用户换个描述。
2. **我方** —— 提交前过一遍最小违规词表;入库时把 `prompt` / `userId` / `albumId`
   写进 ledger 的 `meta`,事后可追责。

上游拒绝的错误码形态必须在上线前摸清(见「前置条件」),不能靠猜。

## 失败路径

| 情况 | 处理 |
|---|---|
| 上游安全拒绝 | 退积分,提示改描述,不计免费次数 |
| 上游超时 / 5xx | 退积分,可重试 |
| 写 R2 失败 | 退积分 |
| 扣费成功但入库失败 | ledger `meta` 留痕,后台可查可补偿 —— 这条最伤用户,必须能人工兜 |

## 实现触点

- **新增 `r2.putObject`** —— 这是**破例**。`src/lib/r2/r2-client.ts` 现在的立场是
  「其余链路一律只发预签名 URL,不代理字节」。破例理由:生成图的字节天生在服务端,
  让浏览器绕一趟意味着海外用户要去下载国内 TOS 的图,不可行。破例范围只限生成图。
- 新增 `POST /api/v1/albums/[uuid]/generate-image`
- 复用 `photoOriginalService.confirm` 落 `album_photos`
- 复用 `creditService` 的 hold/settle/release
- 前端:图槽菜单入口 + 生成弹窗(桌面 EditorPort / 移动 EditView 两端)

## 上线前必须验证的前置条件

这四条 spec 不能假装已经知道:

1. **Gemini 的出图质量一张都没测过** —— 本地被代理挡着(`googleapis.com` 被路由到
   Google 不服务的节点,返回 `User location is not supported`)。必须先把代理规则改通,
   用同一组 prompt 跟 Seedream 对拍一轮。**质量不过关则整个 provider 选择推倒重来。**
2. **Gemini image 的实际单价** —— 上面 10×–15× 的毛利结论依赖它。
3. **Gemini 安全拒绝的错误码形态** —— 审核那节要用。
4. **Vercel 函数时长上限**能否容纳一次同步生成;不能则必须走异步任务(倾向异步)。

## 测试策略

- **prompt 外壳**:纯函数。测承重墙在任何用户输入下都不被冲掉(含注入尝试)。
- **provider**:注入 fake fetch,测两家的响应解析与错误分类(参照已写好的
  `seedream.test.ts`)。
- **扣费**:hold→settle、hold→release、余额不足、并发在途预留四条路径。
- **不测真实出图** —— 要花钱且结果不确定。真实调用留给上线前那轮人工对照。
